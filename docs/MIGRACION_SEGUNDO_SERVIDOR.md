# Migración de LogisTech a un segundo servidor

El servicio público actual usa Lightsail, Caddy, Django y PostgreSQL 17. La migración requiere un destino aprobado con capacidad equivalente, acceso SSH verificado, un operador responsable por host y una ventana para pausar escrituras. Usar el mismo SHA y las mismas imágenes auditadas durante el corte. [Guía AWS](AWS_F7_GUIA.md) · [Backup y recuperación](BACKUP_RECUPERACION_F7.md)

| Fase | Acción | Puerta de control |
|---|---|---|
| Preparación | Instalar Docker y preparar una pila con redes y volúmenes propios. Copiar por SSH imágenes verificadas y la configuración protegida. Provisionar por separado TLS para PostgreSQL, copia cifrada y acceso operativo. | La base de destino queda privada. Se conocen el SHA de despliegue, la huella SSH y el plan de reversión. |
| Ensayo de restauración | Generar un dump lógico y verificar el SHA-256. Transferir la copia cifrada y verificar el checksum. Restaurar primero a una base de nombre nuevo. Ejecutar el manifiesto de integridad y probar permisos y navegación con un nombre de ensayo. | Conteos, restricciones, eventos y movimientos coinciden para las funciones que existan. HTTPS, login, QR y recepción pasan sin alterar el origen. |
| Pausa y sincronización final | Anunciar la ventana acordada. Bloquear escrituras por todos los canales y registrar la hora en UTC. Crear un dump final con checksum, restaurarlo y verificar el manifiesto antes de promover el destino. | El último evento visible coincide en ambos hosts. Conservar la base de origen para recuperar el servicio si antes del corte aparece una discrepancia. |
| Corte | Cambiar el registro A o reasociar la IP según el mecanismo aprobado. Validar TLS con el dominio desde dos redes, salud, estáticos y reglas de acceso. Habilitar escrituras solo en el destino después de las verificaciones de lectura. | Existe una única base autorizada para nuevas escrituras. Se registran la hora de corte y la primera operación válida. |
| Reversión | Antes de aceptar escrituras en destino, reenlazar el tráfico al origen preservado. Si el destino ya recibió escrituras, pausar de nuevo y reconciliar o restaurar esos cambios antes de revertir. | Repetir comprobaciones externas y verificar integridad. Conservar evidencia de la decisión y las operaciones preservadas. |

Medir desde el bloqueo de escrituras hasta la primera escritura confirmada en destino. Registrar por separado en UTC el fin del backup, la transferencia, la restauración, la validación, el cambio de tráfico y la confirmación del cliente. La evidencia del ensayo existente midió 6,429 s de restauración y 19,855 s hasta la validación tras reiniciar. El RTO entre servidores físicos queda pendiente. [Ensayo local](evidencias/semana13-cierre/recovery.json)

`python scripts/verify_second_host_restore.py` ensaya la transferencia entre dos PostgreSQL independientes en Docker, con datos sintéticos y sin puertos publicados. El checksum y el manifiesto coinciden entre origen y destino. La ejecución de semana 16 midió 0,284 s para el dump, 0,335 s para la restauración y 1,093 s hasta comparar ambos manifiestos. Estas cifras son del mismo equipo, sin corte DNS/IP. [Evidencia de semana 16](evidencias/semana16/migracion-local.json)
